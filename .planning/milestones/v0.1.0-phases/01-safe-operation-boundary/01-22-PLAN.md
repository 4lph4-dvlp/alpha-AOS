The debug session confirms the product side is correct and that the race is structurally POSIX-only:

> Session child spawned with `detached:true` → own process group. Descendant spawned `detached:false` → same group. `killTree` does `process.kill(-pid, SIGKILL)` → reaches the group. `close()` resolves on `closed`, which is published from `child.once("close")` — the DIRECT child only. On Windows the same `killTree` branch blocks on `spawnSync("taskkill /T /F")`, which is why the race is POSIX-only.

So this plan does not change what the product terminates. It changes how termination is judged, and it writes down the contract the judgment is judging against.

**Why `process.kill(pid, 0)` succeeding cannot be the oracle.** It answers "may I signal this pid", not "is this process running". It succeeds against a zombie that has already stopped executing, it succeeds against a recycled pid belonging to a completely different process, and it says nothing about *which* process is there. All three of those are exactly the questions the assertion needs answered.

**Why a stalled heartbeat cannot be the oracle either.** The obvious replacement — declare termination when a heartbeat counter stops advancing for some multiple of its period — is unsound in the opposite direction, and the direction it is unsound in is the worse one. The failure this plan exists to fix was observed under the ubuntu runner's ten-file concurrent load. A *live* descendant on a loaded runner can easily fail to get scheduled for a few hundred milliseconds, and a staleness rule would report it terminated. That converts a flaky red into a flaky green, and a safety boundary that fails green is worse than one that fails noisily. Staleness therefore never concludes anything in this design.

**What the oracle actually is.** Two distinct kinds of observation, each used only in the direction it is sound in.

  - **Positive liveness** — the counter advanced, with a matching nonce. This is proof the process is running. Its *absence* proves nothing.
  - **Positive terminal evidence** — a small set of facts each of which can only be true of a process that has stopped: `kill(pid, 0)` raising `ESRCH` (no process holds the pid); `kill(pid, 0)` raising `EPERM` (a process holds the pid but we may not signal it — impossible for our own descendant, so the pid was reused); `/proc/<pid>` absent; the `/proc/<pid>/stat` state character being `Z` or `X`; the `/proc/<pid>/stat` start time differing from the one recorded while the process was known alive (pid reuse); or a **fully-formed** heartbeat line carrying a nonce that is not ours (the file, and therefore the identity, is not the one we are asking about).

Only terminal evidence yields `terminated: true`. The nonce is what makes identity checkable at all: pids are recycled, but the process writing *this* nonce is the process this test started. When the deadline expires with no terminal evidence, the answer is `terminated: false` with the reason recorded — a red that says "could not prove it stopped", which is the honest and safe verdict.

**Why "fully-formed" is load-bearing, and why the heartbeat is published by rename.** A partial read is the one way the foreign-nonce rule could smuggle the original defect back in. If the writer truncated and rewrote the file in place, a reader landing inside that window would observe an empty or half-written file; its first token would not be our nonce; the rule would report a foreign nonce; and `terminated: true` would be returned for a process that is demonstrably still running *and still writing*. That is exactly RC-4's failure direction, and it is load-sensitive in exactly RC-4's way — the more contended the runner, the wider the torn-read window. So the design closes it from both ends, and either end alone would be sufficient:

  1. **The writer never exposes a partial file.** Each beat is written to `<path>.tmp` and then renamed over `<path>`. A rename replaces the directory entry as one step, so a reader sees either the previous complete beat or the new complete beat, never a mixture. A rename that fails (Windows can refuse while a reader holds the file open) is swallowed and the beat is simply skipped; the counter advances again on the next tick, and a skipped beat is a stall, which concludes nothing.
  2. **The reader accepts nothing else.** `parseHeartbeatLine` matches `<nonce> <counter>` followed by a newline and nothing more. Anything shorter, emptier or otherwise unparseable is `null` — no evidence — and never `false`. `heartbeatNonceMatches: false` is reachable only from a complete line whose nonce token is present and differs.

Together with the heartbeat path being named after the nonce it carries, a foreign nonce becomes a fixture-integrity tripwire rather than a liveness path: it can only fire if a well-formed beat carrying some *other* nonce appears in a file only this probe's writer is supposed to touch. The rule stays — identity is the point of the nonce — but it can no longer be reached by a race.

Note which platform each branch serves. On Linux — the platform that failed — a SIGKILLed grandchild is reparented and reaped promptly (`ESRCH`), and while its parent still lives it is a zombie (`Z` in `/proc`). On Windows `killTree` blocks on `taskkill /T /F`, so by the time `close()` returns the tree is gone and `ESRCH` is immediate; Windows has no zombies and no `/proc`, and needs neither. macOS has no `/proc`, and reaches `ESRCH` after launchd reaps the reparented grandchild, well inside a 5s deadline.

  3. `signalProbe === "eperm"` → `terminated`, `"eperm-foreign-pid"`. 그 pid 를 가진 프로세스가 있지만 우리가 시그널할 수 없다 — 우리 자신의 자손에게는 불가능한 상태이므로 pid 가 재사용된 것이다.
  4. `procfs === true && procStat === null` → `terminated`, `"proc-absent"`.
  5. `procStat !== null` 이면 파싱한다. `stat.lastIndexOf(")")` 뒤를 공백으로 자르면 `rest[0]` 이 field 3(state) 이고 `rest[19]` 가 field 22(starttime) 다. comm 필드가 공백이나 괄호를 담을 수 있으므로 **반드시 마지막 `)` 를 기준으로 자른다** — 앞에서 자르면 이름이 이상한 프로세스에서 조용히 오분류된다.
     - state 가 `Z` 또는 `X` → `terminated`, `"zombie"`. 실행을 멈췄고 아직 reap 되지 않았다. `missing[15]` 가 요구하는 구분이 바로 이 줄이다.
     - `recordedStartTime !== null` 이고 지금 읽은 starttime 이 다르면 → `terminated`, `"pid-reused"`.
  6. `counterAdvanced === true` → `running`, `"heartbeat-advanced"`.
  7. 그 외 전부 → `indeterminate`, `"no-terminal-evidence"`.

**7번이 이 설계의 핵심이다.** counter 가 멈춰 있다는 사실은 어떤 경우에도 `terminated` 를 낳지 않는다. 부하 걸린 러너에서 살아 있는 자손이 250ms 동안 스케줄되지 않는 것은 흔한 일이고, 그것을 종료로 읽으면 오라클이 초록 쪽으로 틀리게 된다. 안전 경계에서 초록 쪽 오류는 빨간 쪽 오류보다 나쁘다.

**읽지 못한 heartbeat 도 같은 자리로 떨어진다.** `heartbeatNonceMatches === null` 은 1번(`false` 만 검사)에도, 6번(`counterAdvanced` 는 우리 nonce 로만 참이 된다)에도 걸리지 않으므로, 다른 종료 증거가 없는 한 7번으로 내려와 `indeterminate` 가 된다. 파일이 아직 없는 시작 직후, rename 이 거절된 beat, 그리고 (발행이 원자적이라 일어나지 않아야 하지만) 찢어진 읽기가 전부 여기다. 정체와 미관측은 같은 무게, 즉 무게 없음이다. 이 두 문단을 헬퍼 위 주석에 그대로 적는다.

**관측 쪽 헬퍼.**

    interface TerminationProbe {
      readonly pid: number;
      readonly heartbeatPath: string;
      readonly nonce: string;
      readonly recordedStartTime: string | null;
    }

    /** Reads the start time while the process is still known alive. */
    async function registerProbe(input: { pid: number; heartbeatPath: string; nonce: string }): Promise<TerminationProbe>

    async function waitForTermination(
      probe: TerminationProbe,
      deadlineMs: number,
    ): Promise<{ terminated: boolean; evidence: string; observedMs: number; lastCounter: number | null; advanced: boolean }>

    /** Resolves once the counter has been seen to increase `minAdvances` times. */
    async function waitForHeartbeatAdvance(
      probe: TerminationProbe,
      minAdvances: number,
      deadlineMs: number,
    ): Promise<{ advances: number; lastCounter: number | null }>

`waitForTermination` 은 50ms 간격으로 `ProcessSample` 을 하나 만들어 `classifyProcessSample` 에 넘긴다. `terminated` 가 나오면 즉시 그 evidence 와 함께 돌려준다. 데드라인이 다 차면 `terminated: false` 를 돌려주고, `evidence` 에 마지막 판정("no-terminal-evidence" 또는 "heartbeat-advanced")을, `lastCounter` 와 `advanced` 에 관측을 담는다. 이 반환은 곧 테스트 실패가 되며, 그 실패 메시지는 "멈춘 것을 증명하지 못했다" 라고 읽혀야 한다 — "살아 있었다" 가 아니다. 두 문장은 다른 주장이고 오라클은 전자만 할 수 있다.

샘플을 만드는 방법은 이렇다. `signalProbe` 는 `process.kill(pid, 0)` 을 try 로 감싸 errno 를 읽는다 — 성공이면 `"permitted"`, `ESRCH`/`EPERM` 이면 각각 그 값, 그 외는 `"unknown"`. `procfs` 는 `process.platform === "linux"` 로 정한다. `procStat` 은 `readFile("/proc/" + pid + "/stat", "utf8")` 을 try 로 감싸 실패하면 null. heartbeat 는 `readFile(probe.heartbeatPath, "utf8")` 을 try 로 감싸 실패하면 `null` 로 두고, 성공하든 실패하든 그 값을 그대로 `parseHeartbeatLine(probe.nonce, raw)` 에 넘긴다 — 파싱 판단을 여기서 하지 않는 것이 핵심이다. 반환된 `nonceMatches` 가 `heartbeatNonceMatches` 가 되고, `counter` 는 직전 폴에서 본 값보다 클 때에만 `counterAdvanced` 를 참으로 만든다(`nonceMatches === true` 인 경우에만 유효한 관측이다).

`registerProbe` 는 pid 가 살아 있다고 알려진 순간에 호출한다 — 세션 테스트에서는 자손 pid 를 관측한 직후, `close()` 를 부르기 전이다. 그때 읽은 starttime 이 pid 재사용을 판별하는 기준점이 된다.

**네 호출부를 모두 교체한다.** UAT 는 두 곳을 지목하지만 파일에는 네 곳이 있다 — `:284-291`(인라인 `try { process.kill(childPid, 0) }`), `:328`, `:351`, `:453`. `isAlive` 를 지우려면 네 곳을 모두 처리해야 하고, 그러지 않으면 `:328` 과 `:351` 에서 타입 체크가 깨진다. 그 두 곳은 **기존 단언이고, 그 단언을 지우거나 약화시키는 것은 이 plan 의 금지사항** 이므로 유일한 정직한 처리는 같은 오라클로 **전환** 하는 것이다. 전환은 테스트를 더하지도 빼지도 않으므로 이 plan 의 테스트 증가분은 그대로 **+2**(Task 2 의 통제 테스트 둘)다.

네 곳 모두 같은 골격을 쓴다: 판정할 세션을 열기 전에 `const hb = fixture.mintHeartbeat()`, 세션 args 뒤에 `...hb.args`, pid 를 얻은 직후 `registerProbe({ pid, heartbeatPath: hb.path, nonce: hb.nonce })`, 그리고 세션이 정리된 뒤 `waitForTermination`. 아래는 각 자리에서 그 골격에 무엇이 더 붙고 무엇을 건드리지 않는지만 적는다.

`registerProbe` 는 pid 가 알려진 **가장 이른 시점** 에 부른다. 대부분의 자리에서 그 시점의 프로세스는 살아 있지만, frame cap 자리처럼 `killTree` 가 이미 돈 뒤일 수 있는 곳도 있다. 그 경우 `recordedStartTime` 이 `null` 이 되고, 그러면 pid 재사용 분기 하나만 비활성화될 뿐 나머지 증거는 전부 그대로 유효하다. 기준점이 없다는 사실이 조용히 다른 판정을 바꾸지는 않는다.

`closing a protocol session terminates the whole child tree` (현재 433-456번째 줄): `const hb = fixture.mintHeartbeat()` 로 identity 를 만들고 세션 args 를 `[fixture.descendantScript, fixture.sleepScript, ...hb.args]` 로 연다. 자손 pid 를 관측한 **직후, `close()` 를 부르기 전에** `const probe = await registerProbe({ pid: descendantPid, heartbeatPath: hb.path, nonce: hb.nonce })` 를 부른다 — starttime 기준점은 프로세스가 살아 있는 동안에만 읽을 수 있다.

`const result = await session.close();` 로 결과를 받는다(지금은 버리고 있다). 두 가지를 단언한다.

  - **자손 종료:** `await waitForTermination(probe, CLOSE_TREE_DEADLINE_MS)` 의 `terminated === true`. 실패 메시지는 지금의 `closing a protocol session left a descendant process running` 문구를 유지하되 `evidence`, `observedMs`, `lastCounter`, `advanced` 를 덧붙인다.
  - **전달 경로 확증:** `result.treeTermination` 이 win32 에서 `"windows-tree"`, 그 외에서 `"group"`. 이것이 Task 1 이 만든 값의 쓸모다 — 자손이 사라졌다는 관측과 "그룹 시그널이 실제로 수락됐다" 는 제품 측 보고가 서로를 확증한다. 관측값이 `"not-required"` 라면 직계 자식이 grace 안에 스스로 나갔다는 뜻이고, 그 경우 이 테스트는 `killTree` 를 검증한 적이 없다. 그때는 단언을 약화시키지 말고 **픽스처를 고친다** — `descendantScript` 는 30초를 자므로 그 값은 나올 수 없어야 하고, 나온다면 그것 자체가 새 정보다.

**정리 시그널의 nonce 가드.** 정리 시 `terminated === false` 이고 **직전 샘플의 `heartbeatNonceMatches === true`** 일 때에만 `process.kill(descendantPid, "SIGKILL")` 을 보낸다 — 동일성이 확인되지 않은 pid 에는 시그널을 보내지 않는다. `null`(무증거)도 확인되지 않은 것이므로 보내지 않는다. 이 조건은 현재 코드에 없는 것이고, 없으면 pid 재사용 시 무고한 프로세스를 죽인다. 이 가드는 **시그널을 보내는 모든 자리** 에 있어야 한다. `:328` 과 `:351` 은 원래 정리 시그널을 보내지 않으므로 새로 추가하지 않는다 — 그 자식들은 픽스처의 `track()` 이 teardown 에서 닫는다. 즉 가드가 필요한 자리는 `:284-291` 과 `:453`, 그리고 아래 첫 번째 통제 테스트의 4단계다.

`one unterminated protocol frame past the cap terminates the child instead of growing the buffer` 안의 284-291번째 줄: 같은 헬퍼로 교체한다. 여기서는 `unterminatedFloodScript` 가 heartbeat 를 쓰므로 세션 args 가 `[fixture.unterminatedFloodScript, ...hb.args]` 가 된다. 인라인 `announced`/`announcedPid` 로 pid 를 얻은 직후 `registerProbe` 를 부르고, `await session.closed` 로 결과를 받은 뒤 `waitForTermination` 으로 판정한다. `result.code === "output-cap"` 단언들은 손대지 않는다. 마지막의 `assert.equal(alive, false, …)` 을 `assert.equal(termination.terminated, true, …)` 로 바꾸되 **실패 문구 `a capped protocol session left its child running` 은 그대로 유지** 하고 `evidence`/`observedMs` 만 덧붙인다. 여기서도 `result.treeTermination` 이 `"group"`(win32 는 `"windows-tree"`) 임을 단언한다 — frame cap 핸들러가 부른 `killTree` 가 실제로 그룹에 도달했다는 뜻이다. 정리 시그널을 보낸다면 위의 nonce 가드를 통과한 뒤에만 보낸다.

`a protocol response that never arrives fails on its own deadline and leaves no child behind` 의 328번째 줄: 세션 args 를 `[fixture.silentScript, ...hb.args]` 로 열고, `announcedPid` 직후·`session.close()` 이전에 `registerProbe` 를 부른다. `assert.equal(isAlive(childPid as number), false, "a closed protocol session left its child running")` 을 `await session.close()` 뒤의 `waitForTermination(probe, CLOSE_TREE_DEADLINE_MS)` 판정으로 바꾼다. **실패 문구 `a closed protocol session left its child running` 은 그대로 유지** 하고 `evidence`/`observedMs` 만 덧붙인다. 이 테스트의 나머지 — 타임아웃 rejection, `ProcessPolicyError` 코드, `sha256` 매치, 누적 출력 비보간 단언 — 은 한 글자도 건드리지 않는다. 여기 대상은 직계 자식이므로 `treeTermination` 은 단언하지 않는다: 자식이 grace 안에 스스로 나가면 `"not-required"` 가 정당한 값이고, 그것을 강제하면 없는 계약을 주장하게 된다.

`an absolute deadline settles the session as timed out, and disabling it leaves the frame cap in force` 의 351번째 줄: 이 테스트는 세션을 둘 열지만 판정 대상은 `bounded` 하나뿐이므로 `mintHeartbeat()` 는 **한 번만** 부르고 `bounded` 세션 args 만 `[fixture.silentScript, ...hb.args]` 로 연다. `unbounded` 세션은 지금처럼 `[fixture.unterminatedFloodScript]` 만 넘긴다 — 위의 인자-없음 분기가 그 경우를 no-op 으로 만든다. `boundedPid` 를 얻은 직후, `await bounded.closed` **이전에** `registerProbe` 를 부른다. 기존의 `if (boundedPid !== null)` 가드는 유지하고, 그 안의 `assert.equal(isAlive(boundedPid), false, "a timed-out protocol session left its child running")` 을 `waitForTermination` 판정으로 바꾸되 문구는 유지한다. `unbounded` 세션의 `output-cap` 단언들은 손대지 않는다.

`isAlive` 헬퍼(현재 214-221번째 줄)는 지운다. 네 호출부가 모두 사라지면 남는 정직한 용도가 없다. 지우기 전에 `git grep -n 'isAlive' -- test/protocol-session.test.ts` 로 남은 참조가 0인지 확인한다 — 하나라도 남으면 그것은 아직 전환하지 않은 호출부이고, 컴파일을 통과시키려고 그 단언을 지우거나 약화시키는 것은 이 plan 의 명시적 금지사항이다.

**오라클 자신에 대한 통제 — 테스트 두 개.**

첫째: `the termination oracle distinguishes a running descendant from a terminated one`. 세션을 거치지 않고 `sleepScript` 를 `mintHeartbeat()` 가 준 인자와 함께 직접 spawn 한다(`node:child_process` 의 `spawn` 을 이 테스트 파일에서 import 한다 — `test/process.test.ts:411` 의 직접 spawn 열거는 `src/core/*`, `src/cli.ts`, `src/adapters/*` 만 훑으므로 테스트 파일은 그 대상이 아니다). 순서가 중요하다.

  1. `registerProbe` 로 probe 를 만든다.
  2. `await waitForHeartbeatAdvance(probe, 2, 5_000)` 로 counter 가 **실제로 두 번 이상 증가하는 것을 관측** 하고 `advances >= 2` 를 단언한다. 이것이 "이 픽스처는 정말로 살아서 돌고 있다" 는 적극적 증거다. 이전 설계의 negative control 은 counter 가 *증가하지 않는 것* 을 관측했고, 그래서 스스로가 부하에 민감했다 — 잡아내려는 결함과 같은 결함을 공유하는 통제는 통제가 아니다.
  3. `await waitForTermination(probe, 1_000)` 의 `terminated === false` 를 단언한다. 살아 있는 프로세스에는 종료 증거가 없으므로 이 결과는 부하와 무관하게 성립한다.
  4. nonce 를 확인한 뒤 그 pid 에 SIGKILL 을 보내고, `await waitForTermination(probe, CLOSE_TREE_DEADLINE_MS)` 의 `terminated === true` 를 단언하며 `evidence` 를 실패 메시지에 싣는다.
  5. `context.after` 로 잔여 프로세스를 정리한다.

둘째: `the termination classifier never reads a stalled heartbeat as a stopped process`. `parseHeartbeatLine` 과 `classifyProcessSample` 을 순수 함수로 직접 부르는 테스트이며 프로세스를 띄우지 않으므로 세 플랫폼 모두에서 결정적으로 돈다. 테스트를 새로 더하지 않고 이 하나 안에서 두 함수를 모두 못 박는다 — 둘은 같은 불건전성 방향의 두 절반이고, 나누면 이 plan 의 테스트 증가분(+2)이 바뀌어 `01-23` 의 사슬 검산이 어긋난다. 다음을 단언한다.

  - zombie: `procfs: true`, `procStat` 에 리터럴 stat 한 줄 — state 문자가 `Z` 이고 field 22 가 존재하도록 최소 22개 필드를 담는다 — `signalProbe: "permitted"` → `state === "terminated"`, `evidence === "zombie"`. `kill(pid,0)` 이 여전히 성공하는데도 종료로 읽힌다는 것이 `missing[15]` 의 요구다.
  - 괄호와 공백이 든 comm: `1234 (weird ) name) Z ...` 형태로 같은 단언을 반복한다. 마지막 `)` 기준으로 자르지 않는 파서는 여기서 깨진다.
  - sleeping: 같은 줄의 state 문자만 `S` 로 바꾸면 `state !== "terminated"` 다.
  - **stalled: `signalProbe: "permitted"`, `procfs: false`, `procStat: null`, `heartbeatNonceMatches: true`, `counterAdvanced: false` → `state === "indeterminate"`.** 이것이 이 plan 이 고치는 불건전성 방향의 첫 번째 못이다. 실패 메시지에 그 이유를 적는다 — 멈춘 heartbeat 는 종료의 증거가 아니며, 그것을 종료로 읽으면 부하 걸린 러너에서 살아 있는 자손이 종료로 보고된다.
  - **malformed: 같은 샘플에서 `heartbeatNonceMatches` 만 `null` 로 바꿔도 `state === "indeterminate"`.** 두 번째 못이며, 첫 번째와 정확히 같은 방향을 막는다. 그리고 그 `null` 이 실제로 어디서 나오는지를 `parseHeartbeatLine` 에 대해 리터럴로 못 박는다. 테스트 안에 `const LF = String.fromCharCode(10);` 를 두고 다음 입력이 모두 `nonceMatches === null` 임을 단언한다 — `null`(읽기 실패), `""`(빈 파일), `nonce.slice(0, 8)`(nonce 조차 잘림), `nonce + " 12"`(종결자 없이 잘림, 곧 쓰이는 중인 줄), `nonce + " "`(counter 없음), `nonce + " x" + LF`(counter 가 숫자 아님). 그리고 `"other-" + nonce + " 12" + LF` **만이** `nonceMatches === false` 여야 하고, `nonce + " 12" + LF` 는 `{ nonceMatches: true, counter: 12 }` 여야 한다. 실패 메시지에 이유를 적는다 — 쓰이는 중인 heartbeat 를 낯선 nonce 로 읽으면, 살아서 쓰고 있는 자손이 종료로 보고된다.
  - pid 재사용: `recordedStartTime` 과 stat 의 field 22 가 다르면 `terminated` / `"pid-reused"`.
