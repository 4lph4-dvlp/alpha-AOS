  <decision>How should the CAPA-02 routing contract be reconciled, given that the shipped research skill names tools that do not exist and one the alpha-AOS policy denies?</decision>
  <context>
The pinned discovery server exposes exactly two tools: a web search and a web fetch. Two of the three
identifiers the shipped skill names for it do not exist. The pinned extraction server exposes twenty-five
tools without a key and twenty-seven with one; the alpha-AOS allowlist admits exactly four of them, and
the search tool the skill directs discovery at is not among them, so the proxy refuses it by policy.

The practical consequence is measurable and specific: a CAPA-02 canary that follows the skill as written
calls the denied search tool, receives a policy refusal, and then falls back to a native web search. That
reads on the surface like a routing failure, but it is a contract mismatch between three documents that
nothing currently binds together.

Neither option is a research question — both are internally consistent. What separates them is whether
alpha-AOS's bounded extraction surface stays as narrow as PROJECT.md currently claims.

Editing the skill's bytes is not among the options: CONTEXT.md D-07 and design §5.3 forbid it, and the
identity renderer means target hash equals source hash, so a modified skill would fail its own exact-hash
contract.
  </context>
