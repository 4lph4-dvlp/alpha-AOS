# Automatic weekly dependency promotion

User decision (2026-09-30): every upstream version (major or minor) is promoted
without human approval. Monday: discover + verify on 3-OS CI. Wednesday: if the
Monday verification is green, re-verify and land on main automatically.

## Findings that shape the design

1. Current candidate-PR CI is meaningless for new versions: the CLI only reads
   `stack.lock.json` (src/cli.ts:424), and the PR only changes
   `candidate.lock.json`. New versions must be written into `stack.lock.json`
   on the candidate branch for CI to exercise them.
2. Latest candidate CI run (36405186711) is `action_required` (bot-pushed PR
   needs approval). Fix: call CI as a reusable workflow (`workflow_call`)
   from the scheduled workflow itself, so no PR-triggered run is needed.
3. `scripts/promote-candidate.mjs` default component list omits `exa`.
4. Hardcoded version literals break on every bump:
   - test/catalog.test.ts:67,68,76,108,111 (versions, `ecc-universal@2.2.1`,
     `pi install npm:pi-mcp-adapter@2.36.0`) and :71-74 ECC source/target hash
     literals.
   - test/mcp-fixture.test.ts:34-49 (pi 2.36.0 — synthetic parse fixture; may stay).
   - src/core/mcp-proxy.ts:162 `ROUTING_CONTRACT_MISMATCH.runtime` and
     test/mcp-proxy.test.ts:1457; MEASURED_UPSTREAM_TOOLS (:75-95) records
     measurement versions (historical, leave).
   - test/canary.test.ts exa 3.4.1 strings are captured transcripts (leave).
   - test/promote-candidate.test.ts, test/update.test.ts are synthetic (leave).
   - AGENTS.md:60-65, catalog/canaries.yaml:15 comment.
5. ECC bump needs `pin-pack-skills.mjs write --all` (sourceSha256) and
   recomputed `targetSha256` for the 3 global skills x 5 harnesses via
   `runEccFixture(...).targetHashes`. The deep-research render and the
   routing-contract test (mcp-proxy.test.ts:1498-1530) may legitimately fail on
   a new ECC; that is a correct refusal (CI red -> no promotion, failure email).
6. main has no branch protection; default workflow token is read-only
   (workflows must declare `contents: write`). Pushes made with GITHUB_TOKEN do
   not trigger ci.yml on main, so Wednesday must run full CI itself before push.

### Task 3 — workflows
- ci.yml: add `workflow_call` trigger (inputs: ref) so it can be reused.
- dependency-candidate.yml (Mon 03:17 UTC): stage candidate -> run
  promote-candidate into stack.lock.json on branch automation/dependency-candidate
  (rebased on origin/main) -> commit -> push -> call ci.yml on that SHA ->
  record verified SHA (e.g. git note or artifact `verified-sha.txt`).
- new auto-promote.yml (Wed 03:17 UTC + workflow_dispatch): find Monday's run;
  require success and branch head == verified SHA; rebase branch onto current
  origin/main; `--check-registry`; call ci.yml on the rebased SHA; if green,
  `git push origin <sha>:main` (fast-forward only, fail on race). Failure ->
  workflow fails -> GitHub failure email.
