## Problem

On a fresh install, `applyManagedInstall` fails at the MCP sync step with
`ancestor-changed — component identity changed` (observed 2026-09-26 18:50, durable evidence
`2026-09-26T09-55-04-008Z-09e428f4`):

1. `createManagedInstallOperationPlan` proves each MCP target (e.g. `~/.codex/config.toml`)
   and records its filesystem identity (device/inode) at plan time.
2. The GSD external installs run first inside the same operation — the GSD codex installer
   rewrites `config.toml` with byte-identical content under a new file identity.
3. `applyMcpSync` re-checks the plan-time proof (`assertUnchangedSincePlan`) — the inode no
   longer matches — so the whole managed install fails and rolls back.

The content-based digest checks pass (the rewrite is content-identical), so only the
filesystem-identity check false-positives. The bug was previously masked: earlier attempts
failed at the owned-skill workflow check or were interrupted before the MCP step ever ran.

## Fix

In `applyManagedInstall`, after the external installers complete, re-create the MCP component
plans so their proofs reflect the post-external filesystem, and apply those. The reviewed
aggregate declared the external steps, so their changes are expected; anything that moves a
config after the re-plan is still drift.
