  <action>
Split the two responsibilities the module currently fuses.

Introduce `McpProxyMode` as a string-literal union of `filter` and `observe`, and replace
`runMcpFilterProxy` with `runMcpProxy(serverId, locked, options)` where options carry the mode and an
optional `McpObservationSink`. Keep `runMcpFilterProxy` as a thin deprecated re-export only if a caller
still needs it; otherwise update the caller in `src/cli.ts` is OUT of scope for this plan — leave the
existing export name working. Filtering stays governed by `allowedMcpTools`: a null allowlist means no
filtering, not a throw. The refusal message string stays byte-identical so the stable code contract
Phase 1 D-11 established is preserved.

`McpObservation` is a closed record: `{ server, tool, at, upstreamVersion, outcome }` where `outcome` is
the union `ok` or `denied`. It carries no argument values and no response content — arguments are where
credentials live, and PROJECT.md's secrets constraint forbids a value reaching any observable surface.
`McpObservationSink` is an interface with a single `record(observation)` method so the canary can supply
a file-backed sink later without this module knowing about the ledger.

Hook the recording into the two existing request handlers at :193-200, which already have the tool name
and the upstream client. A denied call records `denied` and then throws, in that order, so a policy
refusal is itself evidence.

`openObservedUpstream(serverId, locked, sink)` exposes the upstream client plus its bounded transport for
a caller that wants to observe without also standing up a downstream server — that is the shape the
canary runtime needs.
