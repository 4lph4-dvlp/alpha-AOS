<objective>
Make a proof state what it INFERRED and what it does NOT cover, in the evidence itself.

Purpose: `03-VERIFICATION.md` closed its blocker by reverting the premature `Complete` rows, and left one
sub-item open under G-1: CAPA-06's `cannot discover` half is proven live by the paired oracle, while its
`or invoke` half is *inferred* from that negative. The inference is sound — a skill a harness never loads
cannot be invoked — and the verifier accepted it, asking only that it be recorded as an inference rather
than left implicit. Separately, Finding I-2 records that the canary runtime materializes an
alpha-AOS-authored routing instruction into its own `CLAUDE_CONFIG_DIR`, so any future CAPA-02 pass proves
routing *inside the canary runtime*, not inside the user's everyday configuration — a scope caveat that
today lives only in a verification report a JSON consumer never reads.

Both are the same defect one layer up from the one this project's PROJECT.md Validation constraint
forbids: a claim whose ground is not carried with it. The ledger already has the right precedent —
`immutabilityWitness.scopeLimit` records what the CAPA-03 witness does not cover, on the row, rather than
leaving it to be assumed. This plan generalises that to the proof itself.

Output: an optional, closed, schema-registered `claimNotes` record on `CapabilityProof`; the CAPA-06
invocation inference written where it is licensed; the canary-runtime scope limit written from the
instruction ids a run actually carried; both rendered on their own lines; and the inference recorded once
in `REQUIREMENTS.md` so a milestone audit reads it beside the requirement it qualifies.

Explicitly NOT this plan: running any paid canary, re-closing G-1 (already closed by commit `5c49abc`),
or changing any requirement checkbox or traceability status.
</objective>
