  <behavior>
    - A file listed in `.gitignore` is `ignored`; a sibling that is not listed is `scannable`.
    - A file created and never committed, and not matched by any ignore pattern, is `scannable` — commit status is never consulted.
    - The same `.gitignore` in a directory with no `.git` entry at all produces the same decisions.
    - A nested `.gitignore` deeper in the tree takes precedence over a shallower one for paths beneath it.
    - A negation pattern re-includes a file whose parent directory is not itself excluded (approved-matcher path), or reports `undecidable` naming the pattern shape (fallback path).
    - A `.gitignore` larger than the declared byte cap, or containing more than the declared pattern cap, is reported `undecidable` rather than partially applied.
    - A deliberately un-ignored build output directory is `scannable` — the decision is membership, not name.
  </behavior>
  <action>
Create `src/core/ignore-list.ts` exporting:

- `type IgnoreDecision = "ignored" | "scannable" | "undecidable"`
- `interface IgnoreRuleSet { readonly directory: string; readonly patterns: readonly string[]; readonly undecidable: readonly string[] }`
- `async function loadIgnoreRules(directory: string): Promise<IgnoreRuleSet>` — reads the `.gitignore`
  in one directory with a byte cap (declare a named constant; 256 KiB is the recommended value) and a
  pattern-count cap (declare a named constant; 5000 is the recommended value). Exceeding either cap
  yields an `IgnoreRuleSet` whose `undecidable` list names the cap that was hit. A missing `.gitignore`
  yields an empty rule set, never an error.
- `function isIgnored(relativePosixPath: string, isDirectory: boolean, stack: readonly IgnoreRuleSet[]): { decision: IgnoreDecision; pattern: string | null }` —
  evaluates the rule sets deepest-first so a nested `.gitignore` wins for paths beneath it, and returns
  the pattern that decided, so a caller can explain the exclusion.

Path inputs are relative POSIX paths measured from the rule set's own directory. Do the native-to-POSIX
conversion once at the boundary; never compare a native-separator string against a POSIX pattern.

If Task 2 installed the approved matcher, `src/core/ignore-list.ts` is a thin wrapper: alpha-AOS keeps
the boundary-proven traversal and delegates ONLY pattern semantics. The matcher does not read
`.gitignore` files and does not walk directories, which is exactly the division this phase wants.
Cap the input length before handing any pattern to the matcher — a hostile `.gitignore` is untrusted
input from the scanned repository.

If Task 2 was skipped, implement the bounded in-house fallback: literal names, directory-suffix
patterns (`build/`), leading-slash anchoring (`/dist`), and a single `*` within one path segment.
Every `!` negation and every `**` yields `undecidable` naming the pattern's shape (its length and
which construct was unsupported), never its raw text. `undecidable` must propagate — it is Phase 1's
D-01 fail-closed rule, and a pattern that could not be decided must never be silently reported as
not-ignored.

Do NOT spawn `git check-ignore` or any other subprocess. D-04 requires the same rule in directories
that are not git repositories at all, where a git query has no answer, and D-08 keeps the preview path
free of subprocesses entirely. Do NOT introduce a hardcoded directory-name prune list: that decides by
name rather than by ignore-list membership, and would make a deliberately un-ignored build directory
invisible as evidence.

Write `test/ignore-list.test.ts` covering all seven behaviours above with real temporary directories

non-git-directory case explicitly: build the fixture WITHOUT running `git init` and assert the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scanned repository `.gitignore` → matcher | Fully untrusted text of arbitrary size and pattern complexity, supplied by the repository being inspected. |
| npm registry → `node_modules` | A new external package enters the reviewed dependency set. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-SC | Tampering | `npm install` of `ignore` | high | mitigate | Package-legitimacy gate: a `gate="blocking-human"` checkpoint precedes install, the exact version is pinned rather than `latest`, `--ignore-scripts` prevents lifecycle execution, and the `dist.integrity` a human approved is re-verified before it is written. |
| T-02-05 | Denial of Service | `loadIgnoreRules` / `isIgnored` in `src/core/ignore-list.ts` | medium | mitigate | Named byte cap and pattern-count cap on every `.gitignore` read; input length capped before any pattern reaches the matcher; exceeding a cap reports `undecidable` rather than partially applying. |
| T-02-15 | Denial of Service | subprocess on the ignore path | medium | mitigate | No `spawn`/`execFile`/`execSync` in the module, asserted by a code-only grep gate in `<verify>`; the preview path stays subprocess-free per D-08. |
| T-02-13 | Information Disclosure | `undecidable` reason strings | low | mitigate | Report the construct and the pattern length only; a raw pattern from a scanned repository never enters a returned reason. |
| T-02-16 | Spoofing | an undecidable pattern read as not-ignored | medium | mitigate | `undecidable` is a distinct third value that propagates to the caller; it is never collapsed into `scannable`. |
</threat_model>
