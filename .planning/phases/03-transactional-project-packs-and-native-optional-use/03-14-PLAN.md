<objective>
Make the machine surface say what it means.

Purpose: `03-VERIFICATION.md` records two findings about the JSON and human surfaces this phase produces,
neither of which is a correctness bug and both of which mislead a reader.

Finding I-1 (`src/core/canary.ts:3405`): `CapabilityReportRow.unsupportedReason` is populated on rows whose
`support` axis reads `supported`. The doc comment is accurate — "Why nothing ran at all. Null when something
did." — but the NAME misleads a JSON consumer, and the human renderer compounds it by opening that line with
the word `UNSUPPORTED` on a row that was never classified unsupported. In a phase whose whole subject is
CAPA-07's rule that a capability must not be collapsed into one misleading state, a line that borrows the
support axis's vocabulary to report a fact about the native-use axis is the same failure in miniature.

The recorded deferred item: `doctor --discovery --json` renders `sweeps[].entries[].unit` as
`[redacted:cycle]`, because `unit` is a redundant alias for the same object as `discovery.unit` and the
observable-serialization seam detects the repeat. Nothing is missing — the full unit is under `discovery.unit`
— but the JSON surface carries a permanently unusable field. The recorded suggested fix is to drop the
redundant alias so an evidence unit lives in exactly one place.

Output: a field and a rendered code that both describe the fact they hold, one evidence unit per place in the
discovery envelope, and the deferred item closed with an explicit resolved status.

Explicitly NOT this plan: renaming `unsupportedReason` anywhere it genuinely means the support axis. The
oracle's and the process adapter's fields keep their names and their meaning.
</objective>
