## The central finding: the instrument is invalid, so the red leg is undecidable

`test/process.test.ts:298` 의 판정부는 `:314-321` 이다. 그것은 `process.kill(<pid>, 0)` 이 던지지 않으면 살아 있다고 결론짓는다.

`process.kill(<pid>, 0)` 이 성공한다는 것은 "이 pid 에 신호를 보낼 권한이 있는가" 에 답하는 것이지 "이 프로세스가 실행 중인가" 에 답하는 것이 아니다. **좀비에게도 성공한다.** 그리고 이 fixture 의 descendant 는 정확히 좀비가 되기 쉬운 모양이다: `runProcess` 는 `spawner.mjs` 를 `detached: true` 로 띄우고(`src/core/process.ts:334`), `spawner.mjs` 는 `sleep.mjs` 를 `detached: false` 로 띄우므로 손자는 같은 process group 에 들어간다. 타임아웃 시 `killTree` 가 그 group 에 `SIGKILL` 을 보내면 둘 다 죽는데, `spawner.mjs` 는 `runProcess` 의 직계 자식이라 node 가 거두고 `sleep.mjs` 는 **아무의 `waitpid` 대상도 아니다** — 부모가 방금 죽었고 init 으로의 reparent 와 reap 사이에 창이 있다.

제품의 계약이 이 사실을 이미 문서화하고 있다 (`src/core/process.ts:690-699`):

> "Reaping is NOT awaited: a grandchild is not this process's child, so it is not a `waitpid` target... A signalled grandchild can therefore still hold a pid as a zombie after `close()` returns, **which is why liveness must be judged by terminal evidence rather than by whether a pid can still be signalled.**"

그러므로 `actual: true` 가 뜻하는 것은 두 가지 중 하나이고, 지금 도구로는 **구별할 수 없다**:

| | 사실 | 지금 관측되는 것 |
|---|------|------------------|
| **(a)** | `SIGKILL` 을 받고 실행을 멈췄지만 아직 거둬지지 않은 좀비 | `process.kill(<pid>, 0)` 성공 → `alive: true` |
| **(b)** | `killTree` 가 group 신호를 거부당해 direct child 로 폴백했고 `sleep.mjs` 는 30초를 온전히 실행 중 | `process.kill(<pid>, 0)` 성공 → `alive: true` |

**기록에 남겨 둘 것.** `01-26-SUMMARY.md` 는 이 실패에 대해 descendant 가 "actually still alive" 였다고 적었다. 그 판단은 위 이유로 증거가 지지하는 것보다 강하다. 그 요약은 나쁜 뜻으로 쓰인 것이 아니고 — 그 시점에 사용 가능했던 유일한 도구가 그렇게 읽혔을 뿐이다 — 다만 이 plan 은 그 과잉 주장을 상속하지 않는다. 지금 말할 수 있는 것은 "현재 도구는 (a) 와 (b) 를 구별하지 못한다" 뿐이다.

## Design decision: the one thing the extracted oracle cannot do here, stated rather than hidden

`test/protocol-session.test.ts` 의 사용 지점들은 세션이 **살아 있는 동안** pid 를 얻으므로 `registerProbe` 가 `/proc/<pid>/stat` 의 start time 을 기록해 두고 pid 재사용을 나중에 탐지할 수 있다.

`runProcess` 의 타임아웃 사이트에서는 그럴 수 없다. descendant 의 pid 는 `result.stdout.excerpt` 안에 있고, 그 결과는 **이미 종료된 뒤에야** 반환된다. 그러므로 `recordedStartTime` 은 null 이거나 좀비의 stat 에서 읽힌 값이고, `pid-reused` 분기는 여기서 사실상 비활성이다.

이것을 감추지 않고 기록하는 이유: 그 분기의 부재는 분류기를 **더 보수적으로만** 만든다. `pid-reused` 는 `terminated` 를 돌려주는 규칙이므로, 그것이 발화하지 않으면 판정은 `terminated` 쪽이 아니라 `indeterminate` 쪽으로 떨어지고 `indeterminate` 는 빨간불이다. safety boundary 에서 틀릴 수 있는 두 방향 중 이쪽이 옳은 쪽이다 — `classifyProcessSample` 의 docblock 이 같은 이유로 stall 규칙을 거부한 것과 같은 논리다. 대신 정체성은 nonce heartbeat 가 담당한다: pid 를 신호하기 전에 `heartbeatNonceMatches === true` 를 확인하는 것은 `protocol-session.test.ts:851-854` 가 이미 하는 그대로다.

## Design decision: how a fail-first signal is obtained on a host that cannot produce the failure

이 개발 호스트는 Windows 다. ubuntu 실패는 여기서 재현되지 않고, `taskkill /T /F` 는 동기적으로 트리를 거두므로 좀비 창 자체가 생기지 않는다.

이 phase 에는 선례가 있다: `01-25` 는 **WSL2 Arch (Linux 6.18, uid 1000 비특권, node v26.8.1)** 를 실제 POSIX 호스트로 써서 fail-first 를 수행했다. 그 요약이 스스로 적어 둔 한계도 그대로 상속한다 — **WSL2 는 ubuntu-latest 가 아니고, macOS 는 거기서 전혀 관측되지 않는다.** 그러므로 WSL2 에서의 초록은 결함이 고쳐졌다는 증거가 **아니다**. 그것이 증명하는 것은 단 하나, 새 계측기가 실제 Linux 커널 위에서 돌고 하중을 받는다는 것이다.

그럼에도 이 단계가 결정적인 이유: WSL2 가 `direct` 나 "deadline 을 넘겨 계속 advance 하는 heartbeat" 를 보고하면, 그것은 **push 를 쓰기 전에 case (b) 가 진단된 것**이다. 그때는 밀지 않는다.
