## Gap being closed

`01-UAT.md` gap `G-01-1`, root cause **RC-4**, `missing` items 14 through 18.

> `test/protocol-session.test.ts:453` 이 `close()` 반환 직후 `process.kill(pid, 0)` 을 한 번만 호출해 생존을 판정한다. 폴링도 pid 동일성 확인도 없다. … 살아있다고 판정되면 그 pid 를 SIGKILL 하므로 pid 재사용 시 무고한 프로세스를 죽인다. `:284-291` 에 동일 패턴이 있다.

The debug session confirms the product side is correct and that the race is structurally POSIX-only:

> Session child spawned with `detached:true` → own process group. Descendant spawned `detached:false` → same group. `killTree` does `process.kill(-pid, SIGKILL)` → reaches the group. `close()` resolves on `closed`, which is published from `child.once("close")` — the DIRECT child only. On Windows the same `killTree` branch blocks on `spawnSync("taskkill /T /F")`, which is why the race is POSIX-only.

So this plan does not change what the product terminates. It changes how termination is judged, and it writes down the contract the judgment is judging against.

**Why `process.kill(pid, 0)` cannot be the oracle.** It answers "may I signal this pid", not "is this process running". It succeeds against a zombie that has already stopped executing, it succeeds against a recycled pid belonging to a completely different process, and it says nothing about *which* process is there. All three of those are exactly the questions the assertion needs answered. The replacement is a heartbeat the fixture process writes itself, carrying a nonce the test generated: a frozen heartbeat is positive evidence that this exact process stopped running, and an advancing heartbeat is positive evidence that it did not.

**판정 헬퍼를 만든다.**

    interface TerminationProbe {
      readonly pid: number;
      readonly heartbeatPath: string;
      readonly nonce: string;

    async function waitForTermination(

동작은 이렇다. 50ms 간격으로 heartbeat 파일을 읽는다. 파일이 없거나 읽을 수 없으면 그 표본은 "정지" 로 센다. 파일이 있으면 nonce 를 확인한다 — nonce 가 다르면 이것은 우리 프로세스가 아니므로 즉시 `terminated: true` 와 그 사실을 담은 `reason` 을 돌려준다(그리고 절대 그 pid 에 시그널을 보내지 않는다). nonce 가 같으면 counter 값을 본다. counter 가 연속 5회 표본(250ms, heartbeat 주기의 5배) 동안 변하지 않으면 `terminated: true` 를 돌려준다. `deadlineMs` 안에 그 조건이 성립하지 않으면 `terminated: false` 와 마지막으로 본 counter 를 담은 `reason` 을 돌려준다.

`process.kill(pid, 0)` 은 판정의 근거로 쓰지 않는다. POSIX 에서 그것은 zombie 에도 성공하고 재사용된 pid 에도 성공하므로 "실행을 멈췄는가" 라는 질문에 답하지 않는다. 보조 정보로 `reason` 문자열에 관측을 적는 것은 허용하되, `terminated` 값이 그것에 좌우되지 않게 한다. 이 이유를 헬퍼 위 주석에 적는다.

**두 호출부를 모두 교체한다.**

`closing a protocol session terminates the whole child tree` (현재 433-456번째 줄): 세션을 열 때 `descendantScript` 에 heartbeat 경로와 nonce 를 넘긴다. `await session.close()` 뒤에 `await waitForTermination({ pid: descendantPid, heartbeatPath, nonce }, CLOSE_TREE_DEADLINE_MS)` 를 부르고 `terminated === true` 를 단언한다. 실패 메시지는 지금의 `closing a protocol session left a descendant process running` 문구를 유지하되 `observedMs` 와 `reason` 을 덧붙인다. 정리 시 `terminated === false` 이고 heartbeat 의 nonce 가 우리 것과 같을 때에만 `process.kill(descendantPid, "SIGKILL")` 을 보낸다 — 동일성이 확인되지 않은 pid 에는 시그널을 보내지 않는다. 이 조건은 현재 코드에 없는 것이고, 없으면 pid 재사용 시 무고한 프로세스를 죽인다.

`an unterminated frame past the cap must settle as capped` 안의 284-291번째 줄: 같은 헬퍼로 교체한다. 여기서는 `unterminatedFloodScript` 가 heartbeat 를 쓰고, `result.code === "output-cap"` 단언들은 손대지 않는다. 마지막의 `assert.equal(alive, false, "a capped protocol session left its child running")` 을 `assert.equal(termination.terminated, true, ...)` 로 바꾸되 메시지의 뜻은 유지한다.

`isAlive` 헬퍼(현재 214-221번째 줄)는 지운다. 두 호출부가 사라지면 남는 정직한 용도가 없다.

**오라클 자신에 대한 통제.** 새 테스트 하나를 추가한다: `the termination oracle distinguishes a running descendant from a terminated one`. 세션을 거치지 않고 `sleepScript` 를 heartbeat 인자와 함께 직접 spawn 한 뒤, 첫째로 짧은 데드라인(1_000ms)으로 `waitForTermination` 을 불러 `terminated === false` 임을 단언한다 — 이것이 negative control 이며, 이것 없이는 폴링 헬퍼가 항상 참을 돌려줘도 나머지 테스트가 초록이 된다. 둘째로 그 pid 를 nonce 확인 후 SIGKILL 하고 다시 `waitForTermination` 을 불러 `terminated === true` 임을 단언한다. `context.after` 로 잔여 프로세스를 정리한다.

**있는 단언을 약화시키지 않는다.** `closing a protocol session terminates the whole child tree` 는 계속 "트리 전체가 종료된다" 를 주장한다. 바뀌는 것은 그 주장을 무엇으로 확인하느냐뿐이다. 이 테스트를 skip 하거나 `context.diagnostic` 으로 강등하는 것은 금지된다 — `descendantPid === null` 일 때의 기존 not-run 분기는 그대로 두되, 그것은 pid 를 관측하지 못한 경우이지 판정을 회피하는 경로가 아니다.
