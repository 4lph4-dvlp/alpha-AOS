<objective>
Build the free, offline, deterministic half of this phase's evidence.

Purpose: CAPA-05 requires the user to SEE a synced capability in the target harness; CAPA-06 requires
the same task outside the project to be unable to discover it. RESEARCH.md Pattern 2 is the
highest-leverage finding of the whole phase: all three target harnesses expose a machine-readable listing
of the skills they loaded, before any model turn, and two of the three cost nothing. That splits the
evidence cleanly — the DISCOVERY axis becomes an automated-suite fact, and the expensive scripted-intent
run is reserved for the INVOCATION axis alone. RESEARCH.md Pitfall 10 is the structural reason this split
is not optional: a bare model turn in an empty fixture cost about thirteen cents, and CI has no
credential at all.

Output: one adapter holding three harness-specific oracle definitions and parsers, recorded fixtures so
the parsers are testable offline on every CI leg, and the paired inside/outside run D-14 requires.
</objective>

Create `src/adapters/capability-oracle.ts` holding `ORACLE_DEFINITIONS` as a
`Record<HarnessId, OracleDefinition | null>`, mirroring the shape of the probe table in

The three definitions, exactly as RESEARCH.md Pattern 2 recorded them from live runs:

- codex: `debug prompt-input` with a placeholder prompt argument, no stdin, zero model cost. The
  subcommand takes no directory flag and reads the process working directory, so the working directory
  is the only positive/negative switch.
- pi: `--mode rpc --approve --no-session`, with a single-line get-commands request on stdin, zero model
  cost. `--approve` is required because pi gates project resources behind a trust decision that defaults
  to asking, and there is no interactive surface in this mode.
- claude: `-p` with a stream-json output format and the verbose flag, one model turn of cost. An empty
  prompt exits non-zero BEFORE the init event is emitted, so a placeholder prompt is mandatory.

antigravity and hermes map to `null`: RESEARCH.md Open Question 1 found no non-interactive entrypoint for
antigravity, and hermes is outside this phase's project-delivery scope. A null definition is the recorded
absence, and `runDiscoveryOracle` returns `unsupported` naming that, never a simulated result.

`runDiscoveryOracle({harness, cwd, timeoutMs})` resolves the executable through the same
`resolveCommand`-over-candidates pattern `src/adapters/isolation.ts` uses, refuses when it is not
directly executable, and launches through `runProcess` with a bounded timeout, a bounded output cap, and
`commandProbeEnvironment` so a read-only probe cannot decide to write into the user's home. It never
calls a child-process API directly. It returns a `DiscoveryResult` carrying the harness, the working
directory, the exit code, the parsed skills, the resolved absolute roots, and `unsupportedReason` /
`unparsedReason` as separate nullable fields.

The A2 rule, stated in code and in a comment: an oracle whose output cannot be parsed sets
`unparsedReason` and yields `unverified` with the stderr fingerprint recorded. It never yields an empty
skill list, because an empty list is the same shape as "the harness genuinely loaded nothing" and the
two facts must stay distinguishable.

Add a test asserting that a harness with a null definition returns `unsupported` with a reason, and one
asserting that a non-existent executable returns `unsupported` rather than throwing.

`parseCodexPromptInput` flattens the message content, slices the skills-instructions block, reads the
roots table and the per-skill lines, and RESOLVES each positional root label to its absolute path before
returning. The labels are positional and shift between directories — outside the project the first label
is a user-level root — so keying anything on the label is a defect, and the resolved absolute path is the
only stable key.

`parsePiCommands` splits the stream on newline only, through a `splitJsonLines` helper. Node's built-in
line-reader module is not protocol-compliant here because it also splits on the line-separator and
paragraph-separator characters, which are valid inside JSON strings; that is pi's own documented warning
and Test 4 pins it. Import no module for this — the helper is a string split.
Read the scope from the nested source-info object, not from the flat field pi's shipped documentation
describes — the docs are out of date and reading the documented field silently yields undefined.

`parseClaudeInitEvent` finds the system-init line and returns its skills and MCP-server arrays. Record
each server's status as a REGISTRATION fact only. Pitfall 5 measured that every server is pending at init
with zero tools present, so the design document's rule that a connected server with zero tools is a
failure cannot be evaluated there; the connection oracle is a separate command and belongs to plan 03-05.

For Pitfall 2, `DiscoveredSkill` carries both `advertisedName` (what the harness said) and `directoryName`
(resolved from the file path), per harness. Do not build a canonicalizer: the three harnesses genuinely
disagree, and a canonicalizer would pick one winner and be wrong on two of three. Do not rename any
directory and do not edit any frontmatter — the directory name is what the lock's source hash keys on,
and the bytes are third-party and immutable under D-07.

## Flagged planner assumptions

- **CAPA-05 edge probe row `unclassified` — UNRESOLVED.** The deterministic probe could not classify CAPA-05 into a shape category and the row is carried forward unresolved rather than auto-resolved with a backstop. Planner reading: CAPA-05 is a provenance-and-use requirement, not a data-shape one. Its predicates are derived from CONTEXT.md D-05/D-07 and RESEARCH.md Pattern 2 instead.
- **CAPA-06 edge probe row `unclassified` — UNRESOLVED** (also flagged in plan 03-03). Its operative edge is the constructed-control rule from Pitfall 3, authored here as a task behaviour rather than as a shape criterion.
- **A1 — cross-OS generalisation of the oracles is unproven.** Every oracle finding is from a Windows 11 host. The recorded-fixture parser tests are portable by construction; the live paired assertions are the part that can differ. A leg where an oracle command is absent or shaped differently must record `unsupported` or `unparsed` with the reason, which is a visible test signal rather than a silent fallback to paid canaries.
- **A2 — the codex oracle subcommand is under a debug namespace and may be renamed.** Mitigated by the unparsed-is-`unverified` rule rather than by pinning a version.
- **A3 — the claude init skills array is assumed to be the complete selectable set, not a filtered view.** The paired positive from the identical command shape is the control; if the array is ever truncated, the positive and negative move together and the pair stays honest.
- **The second codex project root is deliberately NOT added to `PROJECT_SKILL_ROOTS`.** Adding it would widen the receipt schema's reach without adding a harness and complicate removal confinement. The chosen resolution is report-only, which changes no write surface. Recorded here rather than decided silently.
