<objective>
Make the materialized capability visibly alpha-AOS's inside the harness, and prove it does not exist
outside the project.

Purpose: CAPA-05 requires a user to SEE a synced project capability in the target harness with
project-local provenance, and to exercise it through a representative intent-matched task. CAPA-06
requires the same task outside the project to be unable to discover or invoke it. CONTEXT.md D-07 makes
`.alpha-aos/receipts/` the authoritative provenance record and adds a sidecar beside the skill directory
ONLY on surfaces where research proves the harness ignores an unexpected file harmlessly — before that
proof, receipts alone. RESEARCH.md Open Question 2 settled that for two surfaces by placing sidecar files
in a real skill directory and observing the harness list the skill unchanged with empty stderr; the third
surface's documented rule is favourable but was not probed, so it stays receipts-only.

CONTEXT.md D-07 also forbids modifying the skill bytes: design §5.3 and Phase 2's identity renderer both
make a provenance header unavailable, which is exactly why the sidecar exists.

Output: sidecar planning and writing inside the one transaction, the provenance rendering, and the paired
CAPA-05/CAPA-06 evidence unit.
</objective>

Write the six behaviours as failing tests first, then implement.

`SIDECAR_SURFACES` is a per-harness record of whether a sidecar is written, each entry carrying the reason
and the evidence it rests on — the observed tolerance probe for the two proven surfaces, and the
unproven-tolerance reason for the third. Same discipline as the support ceiling: a classification cites
something, and an unproven surface is not upgraded on the strength of a favourable documentation sentence.

`planPackSidecar(packId, harness, targetDirectory, receipt)` returns the sidecar content and its path when
the surface is enabled and null when it is not. The content names alpha-AOS as the owner, the pack id, the
source package and version, the source hash, the receipt path, and the timestamp — the same facts the
receipt carries, so the sidecar is a convenience view and never a second source of truth. Choose the file
name and format and record the choice; CONTEXT.md leaves both to discretion. Prefer a name that a harness
will not mistake for a skill and a format the harness's documented ignore rule covers.

Sidecar writes join the SAME operations list as the skill bytes and the receipt. There is no second
transaction and no post-write step; that is what makes Test 4 pass without any new rollback code.

Extend the removal path so a sidecar is removed with its pack and its path is inside the removal's allowed
roots. Decide explicitly whether the sidecar path is recorded as a receipt target or derived from the skill
target, and record the decision in the summary — a derived path is simpler but a recorded one survives a
future change to the naming rule. Whichever is chosen, Test 6 must hold: a user-modified sidecar refuses
rather than being deleted, the same rule the removal already applies to a drifted skill file.

Do not modify any skill byte. Test 3 is the backstop and it is the reason the sidecar exists at all.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| alpha-AOS sidecar → harness skill loader | an unexpected file inside a directory the harness scans |
| user edits → owned sidecar | a user may modify a file alpha-AOS wrote and expects to remove |
| control directory ancestry → negative proof | the environment decides whether the absence proof is real |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-100 | Tampering | a sidecar a harness misreads as a skill | medium | mitigate | Sidecars are written only on surfaces where tolerance was probed by placing a real sidecar and observing the skill listed unchanged with empty stderr; the unproven surface is receipts-only with a stated reason |
| T-03-101 | Tampering | modifying skill bytes to carry provenance | high | mitigate | Excluded by construction — the sidecar exists precisely because the identity renderer and D-07 forbid touching the bytes; a named test asserts the materialized sha256 equals the locked source hash |
| T-03-102 | Repudiation | a sidecar surviving a rolled-back apply, leaving unowned bytes | high | mitigate | Sidecar writes join the same single operations list; a failpoint-driven rollback leaves none, asserted by a named test |
| T-03-103 | Tampering | a removal deleting a user-modified sidecar | medium | mitigate | The drifted-resource refusal the removal already applies to skill bytes is extended to the sidecar; a named test asserts refusal rather than deletion |
| T-03-104 | Spoofing | a false CAPA-06 negative from an ancestor project skill root | high | mitigate | The checked-ancestor list is required on every negative, and the trust-withheld second negative does not depend on path ancestry at all |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | This phase installs no external package; the materialized bytes come from the pinned lock and their hashes were verified byte-for-byte in RESEARCH.md `## Package Legitimacy Audit`, with no `[ASSUMED]`, `[SUS]` or `[SLOP]` entry |
</threat_model>
