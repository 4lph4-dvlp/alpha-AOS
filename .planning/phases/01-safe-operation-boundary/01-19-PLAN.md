`src/core/path-boundary.ts` 를 고친다. 이 파일에는 정규화 실패를 삼키는 catch 가 정확히 세 곳 있고, 세 곳 모두 다룬다.

**공유 헬퍼를 만든다.** 모듈 로컬 `async function canonicalizeWithMissingTail(pathValue: string): Promise<{ canonical: string; reason: string | null }>` 를 추가한다. `ancestorChain(pathValue)` 를 가장 깊은 쪽부터 거슬러 올라가며 각 조상에 대해 `realpath` 를 시도한다. 성공하면 `canonical = suffix === "" ? resolvedAncestor : resolve(resolvedAncestor, suffix)` 로 계산해 `{ canonical, reason: null }` 을 돌려준다. `suffix` 는 `relative(ancestor, pathValue)` 다.

**실패의 두 종류를 구분하는 것이 이 헬퍼의 전부다.** `realpath` 가 던진 오류의 `code` 를 읽는다.

  - `ENOENT` — 그 조상이 아직 없다는 뜻이다. 이것은 해결 실패가 아니라 "아직 만들어지지 않은 꼬리" 이므로 한 단계 위 조상으로 계속 올라간다. RC-1 의 정상 사례가 정확히 이 경로를 탄다.
  - 그 외 모든 errno (`EACCES`, `EPERM`, `ELOOP`, `EIO`, `ENOTDIR`, …) — 존재하는 무언가를 해결하지 못한 것이다. 위로 올라가면 그 실패를 조용히 덮게 되므로 즉시 `{ canonical: pathValue, reason: "<pathValue> could not be canonically resolved at <ancestor>: <code>" }` 를 돌려준다.
  - 루트까지 전부 `ENOENT` 면 `{ canonical: pathValue, reason: "no ancestor of <pathValue> exists, so it has no canonical form" }` 를 돌려준다.

"없는 것" 과 "읽지 못한 것" 은 다른 사실이고, 이 구분이 없으면 위로 올라가는 동작 자체가 새로운 조용한 catch 가 된다. `reason` 이 null 이 아닌 결과를 정상 값처럼 쓰는 호출자가 없어야 한다.

**첫째 catch — 허용 루트 (현재 243-248번째 줄).** `realpath(configuredRoot)` 한 번 호출과 그 catch 를 통째로 `canonicalizeWithMissingTail(configuredRoot)` 로 바꾼다. `reason` 이 null 이 아니면 `withinRoot` 비교에 도달하지 말고 `unsupported(role, configured, reason, "unprovable-filesystem")` 를 돌려준다. 이것이 RC-1 의 직접 원인이다.

**둘째 catch — 대상 (현재 231-241번째 줄).** 지금은 `components` 배열의 마지막 존재 컴포넌트의 `canonical` 을 써서 계산한다. 같은 결과를 같은 방식으로 얻도록 이 블록도 `canonicalizeWithMissingTail(configured)` 호출로 바꾼다. `reason` 이 null 이 아니면 마찬가지로 `unprovable-filesystem` 로 거부한다. 두 측면이 문자 그대로 같은 함수를 통과하는 것이 이 plan 의 핵심이므로, 대상 쪽 계산을 "지금도 맞으니 그대로 둔다" 로 남기지 않는다 — 비대칭을 코드에서 제거하는 것이 요구사항이다. `components` 배열 자체는 `recheckPathProof` 가 쓰므로 그대로 채운다.

**셋째 catch — 컴포넌트 자기 정규화 (현재 154-159번째 줄).** `classifyComponent` 안의 `try { canonical = await realpath(path); } catch { canonical = path; }` 는 해결 불가 상태를 해결된 것처럼 기록한다. **이 호출은 그대로 둔다** — 여기서 구하는 것은 이미 `lstat` 으로 존재가 확인된 컴포넌트 자신의 정규 위치이지 "아직 없는 꼬리를 붙인 경로" 가 아니므로, 헬퍼를 통과시키면 존재하지 않는 꼬리를 붙이는 분기가 이 자리에서는 영원히 죽은 코드가 된다. 바꾸는 것은 **catch** 다. 헬퍼와 정확히 같은 errno 규칙을 적용한다.

  - `ENOENT` — `lstat` 은 성공했는데 `realpath` 가 ENOENT 라는 것은 대상이 없는 링크(dangling link) 라는 뜻이다. 링크 자신은 존재하고 분류도 됐으므로 지금처럼 `canonical = path` 로 남기고 계속 진행한다. 이것은 오늘의 동작이며, 이 plan 은 이 사례의 의미를 바꾸지 않는다.
  - 그 외 모든 errno — 존재하는 컴포넌트를 읽지 못한 것이다. `unknownReparse` 와 같은 자리의 실패 신호로 바꾼다: 반환 타입을 `PathComponentIdentity | { unknownReparse: true; path: string } | { unprovable: true; path: string; reason: string }` 로 넓히고 `{ unprovable: true, path, reason: "component could not be canonically resolved: <path> (<code>)" }` 를 돌려준다.

**새 신호를 받는 호출부는 두 곳이고 둘 다 고친다.** 하나만 고치면 TypeScript 가 다른 하나에서 컴파일 오류를 낸다.

  1. `provePathBoundary` 의 컴포넌트 루프(현재 218-229번째 줄): `unsupported(role, configured, reason, "unprovable-filesystem")` 로 거부한다.
  2. `recheckPathProof` 의 컴포넌트 루프(현재 303-305번째 줄): 지금 `"unknownReparse" in current` 만 보고 있다. 새 신호에 대해 `{ ok: false, code: "unprovable-filesystem", detail: reason }` 를 돌려주는 분기를 나란히 추가한다. apply 직전에 컴포넌트를 읽지 못하게 된 것은 apply 를 멈출 사유이지 통과시킬 사유가 아니다.

기존 `unknownReparse` 분기는 `unknown-reparse` 코드를 계속 쓰고 이 새 분기와 섞지 않는다 — 두 사유는 다른 것이고 코드가 그 차이를 유지해야 한다.

**끝난 뒤 `realpath` 직접 호출은 파일 전체에 정확히 두 곳이다.** 하나는 `canonicalizeWithMissingTail` 안(대상·허용 루트·recheck 세 경로가 모두 이 하나를 공유한다), 다른 하나는 `classifyComponent` 안(컴포넌트 자신의 동일성 기록 전용)이다. `provePathBoundary`, `recheckPathProof`, `proveOperationPaths` 는 `realpath` 를 직접 부르지 않는다 — containment 비교의 두 피연산자는 언제나 헬퍼에서 나온다. 이 두 자리 외에 새 호출을 만들지 않는다.

**`recheckPathProof` (현재 294-301번째 줄).** `realpath(canonicalRoot)` 호출과 주석뿐인 catch 를 `canonicalizeWithMissingTail(proof.allowedRoot)` 로 바꾼다. `reason` 이 null 이 아니면 즉시 `{ ok: false, code: "unprovable-filesystem", detail: reason }` 를 돌려준다. 지금처럼 "설정된 루트로 되돌아가 아래에서 어차피 검사한다" 로 이어가면, 검사가 실행되는 시점에는 다시 비정규 루트와 정규화된 endpoint 를 비교하게 되므로 같은 결함이 apply 직전 recheck 경로에 남는다.

**바꾸지 않는 것.** `withinRoot` 의 세그먼트 인지 비교, `comparable` 의 대소문자 정책, `outside-configured-root` 분기, `unknown-reparse` 분기, `ancestor-changed` 판정, `proveOperationPaths` 의 role 검사와 `includes` 색인은 손대지 않는다. 이 plan 은 정규화의 대칭성만 고친다.
