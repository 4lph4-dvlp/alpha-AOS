<objective>
Close CR-04 and the three receipt- and claim-shaped defects that land on the same two requirements.

Every repository-supplied document in this phase travels `validateManagedDocument` with a schema —
receipts, the project manifest, the pack catalog, the fact vocabulary. One does not.
`readApprovedProjectPlan` runs a bare `JSON.parse` and checks exactly three things, and everything else
is consumed on trust. `.gitignore` selectively ignores `.alpha-aos/install-state.json`, `journal/`,
`snapshots/` and `evidence/` but NOT `plan.json`, which confirms the artifact is intended to be committed
and is therefore attacker-supplied on every clone.

Two consequences were reproduced. A non-array `satisfied` reaches a `.filter` call guarded only against
nullish values, so `project status` exits 2 with a raw TypeError instead of reporting `STALE` — and it
does so on exactly the stale branch, which is precisely the DETC-06 path. And `StaleReason.sentence` is
built from the approved plan's leaves and rendered verbatim, so a crafted artifact plus a schema-valid
receipt lets a repository put its own prose in front of a user being asked to approve a removal.

Purpose: DETC-06's whole value is that a user can trust a `STALE` report enough to act on it. A report
that crashes on hostile bytes, and a removal prompt whose justification the repository wrote, are the
two ways that trust fails.

Output: `.alpha-aos/plan.json` routed through the strict validator against a closed schema, an
`unreadable` artifact state a user can see, a reconciliation that cannot be crashed by a validated
document, and a support report that compares like with like.
</objective>
