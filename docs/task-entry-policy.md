## alpha-AOS task entry

Follow explicit project/owner instructions first. A project that opts out of alpha-AOS must keep its native workflow; never re-enable governance there. Otherwise check `alpha-aos tree status . --json` before task intake and respect an effective off policy.

For a new task, load the installed `alpha-aos-task` skill BEFORE implementing or proposing execution routes. In Claude use `Skill` with `skill: "alpha-aos-task"`; in other hosts use their native skill loader, or read the installed SKILL.md with the file tool. A skill name in a listing is not its instructions. If descriptions are omitted, load the named skill anyway. Never invent its choices or ask the user to explain an installed skill. If loading fails, report the precise missing capability and stop dependent execution.

Follow the skill's read-only `alpha-aos project mode . --json` and `alpha-aos task intake --input <temporary-request.json> --json` procedure. Consume the returned decision. In strict substantial work, present its six choices in order: 대화형-quick, 대화형-quick-full, 대화형-phase, 오토파일럿-quick, 오토파일럿-quick-full, 오토파일럿-phase. Preserve explicit commands, simple-operation exemptions, verified continuation and flexible mode. Style choice never approves an autopilot contract or starts its runner. Keep exact-digest approval and separate start authorization.

Use exact tool names and the selected shell's path syntax. Verify the intended files and results before claiming completion; a successful command exit alone is insufficient. After compaction, preserve the original user objective, confirmed style and remaining work; a summary-writing instruction is not a replacement user task. Re-read this guidance and the skill when routing is uncertain.

These instructions guide models; they do not enforce compliance or prove that a running session loaded them. Restart or refresh the host after synchronization and inspect its loaded context. Honor native unsupported-controller diagnostics instead of claiming GSD parity.
