<objective>
Close CR-03 and WR-08 — the phase's recurring shape, where `src/core/evidence.ts` builds a rich, honest
record of what it could not decide and the layer above throws all of it away.

`scanProjectTree` records `bounds` (`MAX_SCAN_DEPTH`, `MAX_SCAN_ENTRIES`, `MAX_SUB_PROJECTS`) and
`excludedBoundaries` with reasons, under a module comment stating that a truncated scan which looks
complete is a wrong answer that still looks like a decision. `discoverSubProjects` builds a precise
`DroppedMember[]` and a `declarations` list. `planProjectCapabilities` consumes `discovery.selected` and
`discovery.subProjects` and nothing else; `ProjectCapabilityPlan` has no field for any of it;
`formatProjectPlan` prints none of it. The verifier confirmed the link is absent in every rendering: a
fixture whose only manifest sat behind a nested-repository boundary printed a confident no-pack-qualified
answer with zero disclosure in text, in `--why`, and in `--json`.

The same layer also emits a reason that can be actively false. The reviewer reproduced a failure reason
asserting that none of the declared directories exists under the canonical root, on a fixture where one
of them demonstrably did and had been detected moments earlier.

Purpose: this phase's second success criterion is that a user can inspect why a match happened and why a
near-match did not. An explanation that is silently derived from a tree that was never read is worse
than no explanation, because it is trusted.

Output: a plan value that carries what the scan could not decide, a rendering that shows it in all three
modes, a digest that binds an approval to the completeness of the scan behind it, and a negative reason
that names an exclusion rather than asserting a non-existence.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository tree → scan completeness record | The repository decides, through its size, depth and ignore rules, whether the scan can complete |
| workspace declaration → glob compiler | Declaration entries are repository-authored strings compiled into patterns |
| plan value → approval digest | An approval is only as trustworthy as the completeness of the scan behind it |
