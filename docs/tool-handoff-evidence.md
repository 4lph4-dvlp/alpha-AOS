# Retained tool handoff evidence

Inventory can read a retained npm registry signature without contacting the registry. This verifies only the `package.json` file against the matching file in a retained, registry-signed tarball. A `ready` assessment names that scope; it does not verify the rest of the installation, a build provenance attestation, or any integration or invocation.

The repository-owned `catalog/tool-handoff-policy.json` selects allowed tool-to-package mappings and independently reviewed npm registry public keys. Its initial lists are empty: no installed package is trusted solely because it appears in a lock or carries a key beside its evidence. Reviewers must authenticate keys from the official npm registry, review package identities, expiration, and revocations, and update this policy through the repository's normal review process. Inventory never fetches or refreshes keys. Unsupported sources, missing records, revoked or expired keys, or inaccessible files remain `needs-evidence`.

The read-only record is stored outside the checkout under `<stateRoot>/tool-handoff/<tool-id-with-colon-replaced-by-hyphen>/`. `evidence.json` has exactly `schemaVersion`, `toolId`, `package`, `version`, `integrity`, `keyid`, `signature`, `previousIdentity`, `priorInstallationOwner`, `priorConnectionOwner`, and `userModificationEvidence`. The sibling `artifact.tgz` is the actual npm package tarball; `integrity` is its npm SHA-512 integrity string, and `signature` is the registry's base64 ECDSA signature over `package@version:integrity`. Ownership and modification fields preserve prior observations; they do not claim an npm signature authenticates local ownership. The current implementation requires a known installation owner and an `unmodified` observation, then compares the current manifest bytes with the archive. Raw records or keys supplied in this directory never become trust anchors.

The loader caps compressed and decompressed sizes, accepts only ordinary tar files and directories, rejects duplicate or ambiguous manifests and path links, and reads only the current candidate's `package.json`. More comprehensive transformed-file evidence, direct-binary signatures, npm build provenance and real-host key provisioning remain outside this mechanism; they are not simulated by the signed-manifest result.
