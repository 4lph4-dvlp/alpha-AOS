<objective>
Give the canary somewhere to run that is not the user's machine configuration.

Purpose: CONTEXT.md D-02 puts the observation proxy in the path ONLY during canary runs — everyday
configuration keeps talking to upstream servers directly, because PROJECT.md's key decision is to keep
alpha-AOS a control plane and not an invocation proxy for every tool call. RESEARCH.md's Code Examples
section found the two flags that make this exact isolation available on the canary harness today, and
`src/adapters/isolation.ts:44-52` already constructs one of them. RESEARCH.md Pitfall 10 is why the
discovery sweep and the invocation canary must be two commands: the free one belongs in the automated
suite on every platform, and the paid one is an explicit opt-in that hosted CI cannot run at all — which
is exactly the offline-status-plus-explicit-doctor shape LIFE-02 already describes.

Output: a canary runtime, an assertion that the user's real configuration survives untouched, and two
CLI entry points that keep the free evidence and the paid evidence separate.
</objective>

`createCanaryRuntime({projectRoot, harness, servers, stateRoot})` builds an isolated configuration root
under the managed state root and writes into it one MCP configuration file whose every server entry
launches `alpha-aos mcp-proxy <id>` in observe mode instead of the upstream package directly. Render that
file through the existing per-harness MCP rendering so the server-map key name is the harness's own, not
a second spelling. Credential names travel; credential values never do.

Extend `createIsolationLaunchSpec` with a canary variant rather than adding a second launch path: the
spec already appends the MCP-config and strict-MCP-config flags for the canary harness, and the canary
runtime supplies the config file path. Where a harness has no equivalent strict flag, record a blocked
reason on the spec's existing accumulator instead of pretending the isolation holds — that is the
fail-closed rule the module already follows for sealed mode.

`runCanary({declaration, harness, projectRoot, runtime, sink})` runs the readiness probe first, refuses
with the readiness report when it is not ready, then launches the harness through the runtime with the
declared prompt and collects two things: the observation records the sink received, and the bounded
redacted excerpt of the harness output. The excerpt is evidence about the RUN, never about what the model
said — CONTEXT.md D-01 makes model output text inadmissible as proof, so the excerpt is retained for
diagnosis and is never consulted to decide the invocation axis.

The invocation axis is decided from the observation records alone: the declared expected tool names must
all appear, none of the forbidden names may appear, and the distinct-server count must not exceed the
declared maximum. Return a `CanaryRunResult` carrying the axis, the matched and missing expectations, the
observed distinct-server count, the readiness report, and the recorded provider and model identity.

Add two entry points under the existing `doctor` command.

`alpha-aos doctor --discovery [path]` runs the free paired discovery sweep across every harness with an
oracle definition, pairs each positive with its constructed negative, and records the units in the ledger.
It spawns no model turn, needs no credential, and runs on every platform. It is the command the automated
suite and CI exercise.

`alpha-aos doctor --canary [path] [--harness <id>] [--capability <id>]` runs the declared invocation
canaries. Before running anything it prints what the run would cost — which canaries cost a model turn and
which do not — and which readiness requirements are unmet, so a user is never surprised by a spend. It
refuses with the readiness report when a required credential is absent, using the blocked codes plan
03-05 defined, rather than running and failing.

redaction seam, and both emit the raw axes under `--json` while the human rendering summarises. Follow the
established split: `src/format.ts` owns the human lines, the CLI owns the JSON.

and variable name. An INCOMPLETE evidence unit renders as INCOMPLETE and never as its positive's axis.

Record in the CLI help text that the canary is not a preview and persists a ledger record, so the verb's
contract is visible where a user reads it.
