<objective>
Declare the prompts before spending anything on them, and derive the difference between "blocked" and
"unverified" from a probe rather than from a failure.

Purpose: CONTEXT.md D-12 makes `blocked` and `unverified` carry distinct, load-bearing meanings —
`blocked` means the reason is known and actionable and names the credential VARIABLE and the next step;
`unverified` means nothing was attempted or no evidence exists. RESEARCH.md Pattern 4 found two
off-the-shelf readiness probes that produce exactly that shape and cost nothing to run. CONTEXT.md
`<specifics>` and RESEARCH.md's anti-pattern list both name prompt-rewording as the single easiest way to
turn CAPA-01 and CAPA-02 into theatre; putting the prompts in a reviewed catalog is what makes a reword
a visible diff.

Output: a closed canary catalog, a readiness prober, and the coded blocked vocabulary the whole phase
renders from.
</objective>

| harness readiness output → alpha-AOS | third-party JSON parsed into a blocking decision |

| T-03-41 | Tampering | a canary prompt edited to hint at the tool it should elicit | high | mitigate | Prompts live in a schema-validated catalog so a reword is a visible diff, and a mechanical hygiene test rejects a prompt containing any expected tool name, server id or locked skill id |

## Flagged planner assumptions

- **Prompt storage is Claude's Discretion, resolved to the catalog.** CONTEXT.md leaves the wording and storage of canary prompts open. Storing them in `catalog/canaries.yaml` rather than beside each pack is chosen because the catalog-plus-closed-schema pair is the repository's existing shape for declared policy, and because a reviewed diff is what makes the no-rewording prohibition observable.
- **A7 — a harness may silently fall back to a free model.** Task 2 records the provider and model identity for exactly this reason. A canary result from an unconfigured fallback model is a finding about the model, not about discovery, and the plan requires it to be nameable rather than assumed away.
- **The fan-out judgement rule is Claude's Discretion, resolved as a count of distinct research servers touched for one ordinary lookup.** RESEARCH.md Pitfall 1's second-order note argues against a specific tool sequence, because the discovery server itself also ships a fetch tool, so more than one two-tool path is reasonable. `maxDistinctServers` encodes the count form.
