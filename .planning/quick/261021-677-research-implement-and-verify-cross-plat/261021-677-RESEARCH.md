## Architecture Patterns

Use **plan → authorize → observe → durable intent → one input → fresh observation → append result → verify**. Serialize desktop ownership. Use target-only captures and fail closed on capture/audit failure, expired budgets, stop latch, stale tokens, changed window identity or ambiguous result. Replay verifies evidence without executing input. [ASSUMED: approved design defaults]

Current Driver transport:
- Use one persistent stdio MCP connection. Driver retains legacy `2025-06-18` initialization alongside modern stdio; authenticate any HTTP path separately, but avoid HTTP for this slice. Existing SDK interoperability must be proven. [CITED: https://github.com/trycua/cua/blob/cua-driver-rs-v0.37.0/libs/cua-driver/docs/mcp-protocol-and-skills.md]
- Set bounded mode and reviewed manifest at trusted process startup; include both lifetime bounds, exact app executable resources, allowed tools and no desktop display authority. [CITED: https://cua.ai/docs/cua-driver/guides/permissions]
- Discover actual tools/list schemas. Use get_window_state; semantic element_token or screenshot-pixel coordinates with a one-use capture_id. Never mix desktop points and screenshot pixels or replay stale actions. [CITED: https://cua.ai/docs/cua-driver/reference/mcp-tools/click-and-type]
- Treat foreground takeover as separate authority. Backend errors/expected refusals remain refusals. [CITED: https://github.com/trycua/cua/blob/cua-driver-rs-v0.37.0/libs/cua-driver/rust/Skills/cua-driver/RUNTIME.md]
