## Which branches are reachable, derived from the control flow rather than from the line numbers

The branch under test needs `lstat` to SUCCEED and `realpath` to FAIL with a non-ENOENT errno. A directory with mode `0o000` does not produce that directly — `lstat` on a path *beneath* it fails with EACCES, and `classifyComponent` turns an EACCES from `lstat` into `unknownReparse`, which is a different code and a different fact.

The shape that reaches the intended branch is a **directory link pointing into an unreadable directory**:

- `blocked/` with mode `0o000`, containing `inner/file.txt` created before the mode change, in its own temp tree.
- `<allowed>/link` → `<blocked>/inner`, an ordinary directory symlink inside the fixture's allowed root.
- `lstat("<allowed>/link")` succeeds (the link itself lives in a readable directory), `readlink` succeeds, so the component is classified as a link — and then `realpath("<allowed>/link")` must traverse `blocked` and fails with EACCES. That is `classifyComponent`'s `unprovable` branch at `:200-207`.

That single branch is surfaced at **three distinct call sites**, and each one is a separate test:

| Test | Entry point | Root selection | Site reached |
|------|-------------|----------------|--------------|
| A | `recheckPathProof(proof)` where `proof.allowedRoot` is `<allowed>/link` | allowed root is the link itself, denied *after* the proof was taken | `:352-355` — `canonicalizeWithMissingTail(proof.allowedRoot)` returns a reason, and the recheck refuses **before** the component loop at `:359` |
| B | `provePathBoundary({ path: <allowed>/link/file.txt, allowedRoots: [<allowed>] })`, denied first | `<allowed>` | `:281-283` — the component loop answers on `<allowed>/link` |
| C | `recheckPathProof(proof)` where `proof.allowedRoot` is `<allowed>`, denied *after* the proof was taken | `<allowed>` stays readable, so `:352` passes | `:365-367` — the recheck's own component loop answers on `<allowed>/link` |

Test A is what makes `canonicalizeWithMissingTail`'s non-ENOENT reason (`:140-147`) become an actual refusal instead of a compiler-checked return value, and it is the site that carries the "no containment comparison against a non-canonical root" meaning: at `:352-355` the recheck refuses before `canonicalRoot` is ever assigned.

An ordinary unprivileged user owns the directory and can set its mode, so this runs on ubuntu-latest and macos-latest without privileges. It does **not** work as root (root ignores the mode) and it does **not** work on Windows (a POSIX mode does not deny traversal there), so it is gated — and the gate probes the host rather than trusting a platform name.

## Flagged finding: `provePathBoundary:296-299` is unreachable through the public API

The previous revision of this plan claimed a fourth test could drive `provePathBoundary:296-299` (the allowed-root `canonicalizeWithMissingTail` failure) by naming `<allowed>/link` as the allowed root while targeting a readable path. Read against the source, it cannot, and neither can any other fixture shape. The derivation, which is the reason this is recorded rather than worked around:

1. Root selection at `:260` is **lexical**: `roots.find((root) => withinRoot(root, configured))`. It runs before any canonicalization, and it returns `undefined` — `outside-configured-root` at `:261-266` — for any root that does not lexically contain the target. The previously planned pair (`allowedRoots: [<allowed>/link]`, target `<allowed>/clean/file.txt`) exits there and never reaches `:296`.
2. When selection does succeed, `configuredRoot` is `configured` itself or one of its proper lexical ancestors, so `configuredRoot ∈ ancestorChain(configured)` and so is every ancestor of `configuredRoot`.
3. The component loop at `:271-285` walks that entire chain and calls `classifyComponent` on each member, and `classifyComponent` issues the **same** `realpath` call that `canonicalizeWithMissingTail` would issue at `:296`.
4. Therefore, for `:296-299` to fire, `realpath` must fail non-ENOENT at some ancestor of `configuredRoot` — but the loop already visited that ancestor and returned `unknown-reparse` at `:274-279` (when `lstat` itself failed non-ENOENT) or `unprovable-filesystem` at `:281-283` (when `realpath` failed non-ENOENT). Either way the function returned before `:296`.

The only way to reach `:296-299` is for the filesystem to change between `:285` and `:296` — a TOCTOU race no fixture can drive deterministically, and not something to simulate by monkey-patching `node:fs/promises` in a suite whose whole subject is that the real filesystem is the oracle.

**Disposition: flagged, unresolved, and deliberately not covered.** The branch is *ordered-out defensive symmetry*, not dead code: it becomes live the moment the component loop is reordered, narrowed, or removed, which is exactly the kind of edit a later phase might make. This plan modifies no `src/`, so nothing is deleted and no comment is added at the site. What it does instead is record the derivation above in `01-25-SUMMARY.md` as a source-grounded finding, so a later plan decides on the record rather than rediscovering it. Its behavioral twin — a root that cannot be canonicalized refuses instead of being compared unresolved — **is** proven, by Test A at `recheckPathProof:352-355`.

관측된 코드가 `unprovable-filesystem` 이 아니면, 그것은 기대값을 고칠 이유가 **아니다**. 그때는 편집을 멈추고, 관측된 코드와 어느 테스트였는지를 요약에 기록하고 보고한다 — 제품이 위 표의 제어 흐름과 다르게 동작한다는 뜻이고, 그것은 테스트가 아니라 진단이 처리할 새 정보다.

**픽스처 헬퍼 두 개.** 이 파일의 기존 `tryDirectorySymlink` / `tryFileSymlink` 와 같은 모양의 모듈 로컬 async 헬퍼를 추가한다. 두 개로 나누는 이유는 테스트 A 와 C 가 **proof 를 먼저 얻고 그 다음에 거부**해야 하기 때문이다 — 한 헬퍼가 생성과 거부를 함께 하면 그 두 테스트를 쓸 수 없다.

  - `makeDeniableTree(context)`: `mkdtemp` 로 **자기 소유의** 임시 트리를 만들고, 그 안에 `blocked/inner/file.txt` 를 만들고, `context.after` 에 단 하나의 훅 — `chmod(blocked, 0o700)` 을 시도(실패는 삼킨다)한 뒤 `rm(root, { recursive: true, force: true })` — 을 등록하고, 아직 전부 읽을 수 있는 상태로 `{ root, blocked, inner, innerFile }` 를 돌려준다. 던지지 않는다.
  - `denyTraversal(tree)`: `chmod(tree.blocked, 0o000)` 후 `realpath(tree.inner)` 를 호출해 호스트가 **실제로** 거부하는지 묻는다. `EACCES` 또는 `EPERM` 이 던져지면 그 코드 문자열을 돌려주고, 해석에 성공하거나 다른 errno 면 mode 를 `0o700` 으로 되돌리고 `null` 을 돌려준다. 플랫폼 이름이나 uid 를 믿지 않고 호스트에게 직접 묻는다 — 이것이 이 헬퍼의 요점이다. 던지지 않는다.

**정리 보장 — 훅 순서에 의존하지 않는다.** `node:test` 는 `context.after` 훅을 **등록 순서대로** 실행한다(설치된 Node v24.13.1 에서 측정함). `createFixture` 가 자기 `rm(root, …)` 을 먼저 등록하므로, mode 복원을 나중에 등록하면 그 `rm` 이 **먼저** 돌아 `0o000` 디렉터리를 내려가려다 EACCES 로 실패하고, 지울 수 없는 트리가 남는 동시에 훅 실패로 테스트까지 빨개진다. 그래서 거부되는 디렉터리를 fixture root 안에 두지 않고 `makeDeniableTree` 의 자기 트리에 두고, 복원과 삭제를 **한 훅 안에서** 한다. fixture root 에는 심링크만 남고 `rm` 은 심링크를 따라가지 않고 unlink 하므로, 두 훅의 상대 순서는 무관해진다. 이 문단의 요지를 헬퍼 옆 주석에 남긴다.
